# Publish VSIX

A GitHub Action that publishes a prepared VSIX to Visual Studio Marketplace,
Open VSX, or both. Transient failures are retried, and existing versions are
skipped by default so interrupted releases can be rerun.

## Usage

Build your extension first, then pass its VSIX path and registry tokens:

```yaml
- uses: jolars/publish-vsix@v1
  with:
    vsix-path: editors/code/panache-linux-x64.vsix
    marketplace-token: ${{ secrets.VSCE_PAT }}
    open-vsx-token: ${{ secrets.OVSX_PAT }}
```

Omit a token to skip that registry. At least one token is required. The action
attempts each requested registry even if another fails, then fails the step if
any requested publication remains unsuccessful.

Platform and prerelease information come from the VSIX. Package each target with
`vsce package --target <platform>` and, when appropriate, `--pre-release`. Keep
platform publishing jobs serialized with `strategy.max-parallel: 1` to avoid
concurrent writes to the same Open VSX version record.

## Inputs

  | Input               | Default  | Description                                                                   |
  | ------------------- | -------- | ----------------------------------------------------------------------------- |
  | `vsix-path`         | Required | Path to one prepared VSIX, relative to the repository workspace.              |
  | `marketplace-token` | Empty    | Marketplace personal access token. Omit to skip Marketplace.                  |
  | `open-vsx-token`    | Empty    | Open VSX personal access token. Omit to skip Open VSX.                        |
  | `skip-duplicate`    | `true`   | Treat an existing version for the package's platform as success.              |
  | `max-attempts`      | `4`      | Attempts per registry, including the first attempt. Must be between 1 and 10. |

The action masks tokens and passes them through environment variables rather
than shell arguments.

## Outputs

`marketplace` and `open-vsx` each report `success`, `failure`, or
`not-requested`. A duplicate skipped by the publishing client counts as
`success`. Input validation failures do not produce registry outputs.

## Retry behavior

Timeouts, connection resets, temporary DNS failures, HTTP 408, HTTP 429, and
HTTP 5xx responses are retried. Other errors, including authentication,
permission, and manifest errors, fail immediately for that registry.

Retries wait 15, 30, and then 60 seconds. Additional attempts keep the 60-second
delay. A Marketplace `Retry-After` header can extend a wait to five minutes; a
longer requested wait fails the publication so a later workflow run can retry
it. Open VSX's client does not expose response headers.

Every attempt reopens the same package and repeats the client's duplicate
handling. This covers a lost response after the server has accepted an upload.

## Runtime

This composite action sets up Node.js 24 and installs its own locked
`@vscode/vsce` and `ovsx` dependencies inside the action directory. It does not
require either client in your extension's dependencies. There is no bundled
JavaScript build to regenerate. Dependabot tracks the clients and GitHub Actions
dependencies.

CI exercises the Node.js code on Linux, macOS, and Windows. Tests use local
registry servers and fake credentials; they never publish a real extension.

## Development

The Nix/devenv configuration provides Node.js and workflow and shell linters.
Panache must also be on `PATH` for Markdown checks.

```bash
npm ci --ignore-scripts
npm run check
actionlint
shellcheck scripts/update-tags.sh
shfmt -d scripts/update-tags.sh
panache format --check .
panache lint .
```

Use `npm run format` and `panache format .` to apply formatting.

## Releases

Versionary manages `version.txt` and `CHANGELOG.md` through release pull
requests after CI passes on `main`. The setup follows `setup-benchopt`, using
Versionary's `simple` strategy and stable `v1`/`v1.x` tags.

The GitHub repository needs a `RELEASE_TOKEN` secret with permission to push
release branches and tags, manage pull requests, and create releases. Its token
must allow downstream tag workflows to run. Configure that secret and allow
GitHub Actions to create pull requests before enabling releases.

Stable `vX.Y.Z` tag pushes update the floating major and minor tags. Prerelease
tags are excluded, and maintenance releases cannot move newer floating tags
backward. `CHANGELOG.md` is generated by Versionary; do not edit it manually.
